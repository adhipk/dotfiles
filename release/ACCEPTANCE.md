# Native 1.0 acceptance and publication protocol

All catalog utilities and every enabled desktop/terminal module in `support-matrix.json` are required through the `consumer-desktop` profile. The only exclusions are the already disabled Hermes adapter, Hyperspace, and Projects; these remain dormant optional integrations. The gate compares module enablement against checked-in defaults so new enabled utilities cannot silently escape acceptance. A development build, mock launchd test, existing configured Mac, green local suite, or signing workflow is insufficient desktop acceptance. Keep `VERSION` at its development prerelease until the complete stable candidate can be reviewed. Local artifacts from a dirty checkout are useful for development and always fail the release gate.

## Candidate and CI

1. `make source-materials` assembles the pinned Pandoc repository archive, upstream recipes/notices and a declared dependency inventory for distribution. The material is currently partial: exact official-binary build/dependency provenance is missing, as detailed in `vendor/pandoc-source/SOURCE_PROVENANCE.md`. The final release gate rejects this known-incomplete source state even if JSON license attestations say passed. Complete Apache-2.0 `LICENSE`, `NOTICE`, third-party notices and distributable corresponding-source evidence for bundled GPL components. Verify exact pinned source and build information for any modified GPL binary. Store evidence links in acceptance JSON; including notices alone does not complete the source gate.
2. Review and commit the complete candidate. `vendor/pandoc-source/OWN_BUILD.md` describes the source-built alternative and `SOURCE_REVIEW.md` records the actual ARM capture and explicit erf notice gap. `branch-protection-plan.json` contains the proposed GitHub protection body: strict both-tier checks, conversation resolution, administrator enforcement and no force pushes/deletions. Reviewer-count requirements are left unset for this personal repository. Read current protection with `gh api repos/OWNER/REPO/branches/BRANCH/protection`; applying the proposal is an explicit repository-administrator operation and has not been performed. Require both **Native app and extension contracts** and **Existing integration contracts** on the protected release branch. Record the successful GitHub run URL and full commit in JSON. Branch protection is an administrator action, not a side effect of running local tests.
3. Configure the GitHub `release-signing` environment with secrets `DEVELOPER_ID_P12_BASE64`, `DEVELOPER_ID_P12_PASSWORD`, `DEVELOPER_ID_IDENTITY`, `NOTARY_APPLE_ID`, `NOTARY_APP_PASSWORD`, `APPLE_TEAM_ID`. Never store credentials or certificates in the repository.
4. Run **Signed release candidate** with the full immutable app commit and `pandoc_source_run_id` identifying a successful **Pandoc source build** run with both native jobs passed. The workflow downloads that immutable architecture artifact and packages its verified binary/source sidecar. The environment exists without approval protection or credentials; optional environment protection is a separate administrator decision. It builds independently on ARM and Intel, verifies the clean signed archives, notarizes, staples, and uploads artifacts. It does not create a tag or GitHub release. A certificate or Apple service failure blocks the candidate.
5. For local signing use `python3 scripts/build-app.py --sign 'Developer ID Application: …'`, `make release-candidate-check`, then `DOTFILES_NOTARY_PROFILE=existing-profile bash scripts/notarize-app.sh`. This explicitly uses the existing Keychain profile; bootstrap never signs or notarizes.

## Clean desktop protocol

Copy `acceptance-template.json` to an evidence location outside the checkout. The template starts entirely pending. Exercise the **downloaded, stapled ZIP** on a clean supported macOS device for each architecture (ARM and Intel), without personal dotfiles, utility checkouts, Brew packages, or copied configuration. Record tester, exact macOS version, candidate commit, version, ZIP SHA256, and recordings/log paths. Testing newer macOS versions does not independently establish minimum-version support; include minimum-supported-OS coverage in the retained evidence before claiming it.

For each device:

- Download over a browser so quarantine is applied. Verify checksum, extract and launch through Finder, confirm Gatekeeper accepts it and shows the expected signed publisher. Do not remove quarantine attributes or disable Gatekeeper.
- Exercise first launch, dependency setup and every catalog utility. Start without its dependencies, follow the documented install/provisioning flow, then run every exposed action with representative input. Include Markdown clipboard selection/paste, app focus and all app/window paths, scratchpads, notifications, timer lifecycle, TTS, task storage, default-app changes and unescape. Record outputs and visible desktop behavior under each utility's ID.
- Deny permissions first, confirm the error and guided retry, then grant only the documented permissions. Verify shortcuts register, conflicting shortcuts report errors, disabled shortcuts stop working and app-local keys remain intact.
- Enable and disable Open at Login, log out/in (or reboot), and verify one instance and correct login behavior. Enable each background service, kill its child, verify the documented crash/restart behavior and bounded retained logs, then disable it and verify launchd has no remaining owned job.
- Upgrade an installed previous version with non-default settings. Interrupt the update at documented recovery boundaries and repeat startup; verify no orphan temporary state, lost configuration, or conflicting service instance. Run rollback and verify the previous version/settings/services. Where a feature is inapplicable to a command-only utility, describe that in the evidence rather than silently skipping the device-level check.
- Uninstall each utility and the app. Confirm owned shortcuts, launchd jobs and login registrations disappear. Confirm user-owned files and upstream project checkouts remain as documented. Reinstall once and confirm a clean usable state.

- Review `bootstrap.sh --consumer` planning output before applying the consumer profile. Install on the clean device, exercise interruption/resume of dependency/project/configuration setup, and verify each enabled module separately under `modules`. This includes gh-create-repo, qutebrowser shortcuts, window/space/display management, appearance, terminal window types, tmux/session/Yazi controls, control panels, settings and shortcut guide; catalog records alone are insufficient.
- Repeat consumer profile setup over existing non-default machine preferences and an installed previous release. Verify resume, update, rollback and preservation of machine preferences and user-owned projects/files. Verify consumer uninstall removes owned integration and services while preserving documented user data. Link before/after preference snapshots and installer recovery logs for each dedicated consumer check.

Set a record to `passed` only after reviewing its evidence. Include precise steps and observed results in linked recordings/logs. Any failure remains pending/failed and blocks publication. Both architectures must be completed before publishing a paired release; supply both architecture-specific artifact directories to the final gate because the checksums differ. The final gate rejects a single-architecture invocation; candidate verification alone remains per artifact.

## Final gate and explicit publication

After changing `VERSION` to the intended stable version, create a **new clean commit and new signed candidate**, rerun CI, and repeat acceptance against its exact SHA256. Prerelease evidence does not apply to a rebuilt stable archive. Download build metadata, checksum and notarization receipt with each candidate and place them in its own directory.

```
python3 scripts/verify-release.py --dist /path/to/arm64-candidate --dist /path/to/intel-candidate --acceptance /path/to/acceptance.json
```

The gate independently extracts each ZIP, checks the Developer ID signature, catalog completeness, exact notices/support policy, archived release/minimum-OS plist, every bundled Mach-O architecture and pinned dependency metadata/signed-binary digest, Apple stapling and Gatekeeper, clean source commit, metadata/checksums and evidence records. The final gate also queries GitHub through an authenticated `gh` session and requires the referenced Validate run to match the exact candidate commit and contain successful jobs for both CI tiers. Desktop/license JSON records remain human attestations; the gate does not inspect recordings to prove those attestations are truthful. A reviewer must open retained desktop and license evidence before publication. Missing GitHub authentication or a failed remote query blocks the final gate.

Only after both pass, explicitly approve publication of the immutable tag, architecture-labeled ZIPs, checksums, metadata, Apple receipts, corresponding-source materials and release notes. Do not rebuild after acceptance. Validate a downloaded published artifact once more with the same receipt and checksum. Keep development packaging, personal `bootstrap.sh`, and public app installation distinct.

Own-source ZIPs are read from each candidate directory by the checksum-bound `sourceMaterialsArchive` metadata. To use external ZIP locations, repeat `--source-materials` once per architecture. Complete `sourceReviews` records for both raw-binary/source-ZIP pairs; review must address source/runtime closure, license notices and the explicit erf notice gap. The final gate downloads the exact source-build run artifacts and compares raw binary and source-ZIP hashes, so an unrelated successful CI URL cannot substitute for the reviewed capture. Official binary mode retains its known-partial source rejection.
