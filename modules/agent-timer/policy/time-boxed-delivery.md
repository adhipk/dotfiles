## Time-boxed Delivery

- `TASK_TIMELIMIT_SECS` is the wall-clock length of each recurring checkpoint block for every nontrivial work turn. The machine default is 600 seconds; a session may override it with another positive integer. **Codex is the default terminal agent** and arms the timer automatically through its global prompt hook. Before editing, delegating, or starting long-running commands in another supported terminal agent, run `agent-timer start` from the active working directory. An invalid or non-positive value is a configuration error: report it instead of pretending a timer is active.
- One root turn owns one timer and a sequence of immutable checkpoint blocks. Subagents and user steering messages inherit the current block. Tool calls, retries, context compaction, incoming requests, and reviewer handoffs do not reset or extend it. Only checkpoint expiry advances the same timer into its next block; the machine default immediately re-arms 600 seconds.
- Budget for delivery, not only implementation. Produce a reversible tangible slice early. When the warning steer arrives, avoid expanding scope and delegate read-only checkpoint preparation to an available subagent while the root continues safe in-scope work. The subagent gathers the artifact, fastest relevant validation, working-tree state, canonical task status, and next step without making competing edits.
- When the checkpoint steer arrives, finish any in-progress atomic write and preserve the tangible artifact. Use the prepared status if it is ready; otherwise post a minimal root-collected checkpoint as commentary at the next safe boundary and let an available subagent enrich a later update. Never wait for checkpoint collection before continuing the open canonical task. The same timer has already re-armed a fresh block. Never use a final response or end the Codex turn or tmux session because of a checkpoint.
- A checkpoint must identify the tangible artifact or change produced, validation completed or still failing, the current working-tree state, open canonical task IDs, and the next concrete step. Never claim unvalidated work is complete, never mark unfinished work done, and never discard useful progress merely to leave a clean tree.
- Checkpoint expiry is never a termination condition or blocker. Do not stop merely because a block elapsed. Stop only when the requested outcome is complete or the work meets the existing genuinely-blocked definition; otherwise keep the canonical task open and continue in the newly armed block.

## Incoming Requests During Active Work

- Assess each incoming request against the active objective, implementation difficulty, architectural fit, dependencies, end-user experience, and remaining time.
- Integrate it when it produces a more coherent result without putting the current checkpoint at risk. Explain the integration and trade-offs in plain language.
- Push back when it conflicts with the existing design, duplicates native tooling, harms the user experience, or cannot fit safely inside the remaining budget. Offer the smallest coherent alternative.
- If an addition should be deferred, capture or reuse its distinct canonical todo entry and continue the highest-value deliverable. Do not silently extend the timer.
