# Nearly-Headless Product Thesis

Nearly-headless is an agent-authored HTML workspace, not chat with nicer message
cards.

The app shell is the control plane: the user creates tasks, chooses provider
sessions, answers prompts, reviews progress, and redirects the agent. The task
artifact is the output plane: a durable HTML surface that should remain useful
without reading the transcript.

## Core idea

The agent's primary directive is to convey the work in the most helpful form it
can make.

That form may be a concise note, but it may also be a report, table, diagram,
timeline, status dashboard, visual diff, inspector, simulator, parser, wizard,
benchmark viewer, or one-off browser tool. The canvas is blank on purpose: the
agent chooses or invents the representation that fits the job.

## Design model

```text
user intent
  -> agent chooses representation
  -> existing primitives if they help
  -> task-specific HTML/CSS/JS when they help more
  -> durable artifact in .hyperspace/
  -> user comments, interacts, or submits generated inputs
  -> agent revises the artifact
```

The durable state is HTML. When a tool needs structured data, embed it locally in
the page, usually as JSON:

```html
<script type="application/json" data-state>
  { "items": [], "selection": null }
</script>
```

Rendering can be plain HTML, native custom elements, inline scripts, canvas, SVG,
or CDN-backed browser libraries when the dependency earns its weight. No React,
no build step inside generated artifacts.

The standalone app may use its own frontend stack. Generated artifacts remain
small enough for provider agents to inspect and revise.

## Components

`<hs-*>` components are reusable primitives, not a component palette for users
and not a boundary for agents.

Use existing components for common structures such as callouts, findings,
comparisons, and details. Add a reusable `hs-*` component only when a pattern is
likely to recur across artifacts. Keep one-off task-specific UI local to the
artifact.

There is intentionally no user-facing "add component" UI. The user should work
on intent and content; the agent should author the appropriate surface.

## User interaction

The artifact surface is not a general-purpose HTML editor. Full live editing
makes the user responsible for the document structure, which is the agent's job.

Users should be able to:

- interact with controls, forms, filters, diagrams, and tools generated by the
  agent
- send a default message to the agent from the app shell
- focus the message box, click artifact elements, and insert DOM identifiers
  such as `@dom:hs-...` or `#existing-id` into the message
- click Comment, select any meaningful part of the artifact, and leave feedback
  for the agent
- save those interactions/comments so the agent can revise the artifact

If the agent needs direct input, it should generate the right input surface in
the artifact: a text box, form, choice set, checklist, file picker, or custom
control. User input then becomes part of the saved HTML state.

Messages are saved as `hs-message` nodes in the artifact. If a message references
a DOM identifier, resolve it from the saved HTML and infer the surrounding
context from nearby content and structure.

Comments are saved out-of-flow in an `hs-comments` container and point back to
targets with `data-comment-for`. They should not alter the artifact layout.

## Good artifacts

A good nearly-headless artifact:

- is useful without the chat transcript
- preserves enough context and state to resume the work later
- exposes the next useful actions, decisions, or controls
- asks for input with explicit UI when input is needed
- uses spatial or interactive structure when linear prose would be weaker
- keeps implementation small enough for an agent to inspect and revise quickly
- saves as valid, balanced HTML

## Non-goals

- Rebuilding a chat client
- Forcing every output through predefined cards
- Making users hand-edit generated HTML structure
- Maintaining a large frontend app or build pipeline
- Treating generated HTML as decoration around a transcript

## Operating rule

If prose is the clearest artifact, write prose. If a tool, diagram, table,
inspector, or custom interface is clearer, build that instead.
