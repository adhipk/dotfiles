Managing coding agent sessions

The problem · worker vs manager agents · nearly-headless · why HTML artifacts live outside Codex/Claude

Core insight: HTML is the right medium for progress and steering (Unreasonable Effectiveness of HTML) — but the coding agent should not be the one building it. A separate manager agent watches sessions and maintains artifacts while workers stay focused on code.

What's broken today

  • Session sprawl — multiple Codex and Claude sessions running; hard to know which is doing what.
  • Wall-of-text progress — wait minutes, get a stream you can't scan; project status isn't visible.
  • No pending queue view — what's blocked, waiting for you, or idle across sessions?
  • Provider juggling — switching Codex vs Claude, models, and project context is manual pain.

Why markdown / terminal chat doesn't fix this

Long markdown plans are hard to scan. Terminal streams have no spatial structure, no cross-session view, and no durable interactive controls. The HTML article argues for tabs, tables, diagrams, and two-way controls — but generating those inside every coding turn burns tokens and slows the worker.

Two-agent model

Worker agents

Codex, Claude Code, Cursor CLI — do the actual repo work.

  • Edit files, run tests, implement features
  • Stream raw progress to the runtime
  • Do not maintain HTML dashboards
  • Do not spawn a new artifact every commit

Manager agent

nearly-headless — watches workers, maintains the UI layer.

  • Central session/provider/task registry
  • Generates & updates HTML progress artifacts
  • Surfaces pending input, approvals, blockers
  • Routes your feedback back to the right session(s)
Anti-pattern: asking Codex/Claude to "make an HTML status page" inline. Slows the worker, costs tokens, produces a new page on every minor update, and competes with the actual task.

Instead: a local manager (nearly-headless, optionally backed by a lightweight local model like gemma-gem) subscribes to session events and incrementally updates a small set of durable artifacts — project dashboard, task detail, decision forms.

What HTML artifacts are for

Per the HTML effectiveness model — applied here by the manager, not the worker:

  • Progress at a glance — status dashboards, timelines, diff summaries across sessions
  • Steering — forms, checklists, priority sliders that round-trip as structured prompts
  • Session groups — one project view over many provider sessions
  • Pending queue — what's waiting on you, what's blocked, what's done

Artifacts update on meaningful milestones — not every tool call.

Where t3code and ACP fit (reference only)

t3code solves a narrower problem: one web GUI talking to one Node server that wraps provider CLIs. Good reference for thread/turn orchestration and ProviderAdapter. We go further: HTML-first (not chat), manager/worker split, and optional multi-process bus.

ACP standardizes editor↔agent wire protocols. Useful later as a provider adapter inside nearly-headless — not a replacement for the manager layer or agent-comms.

Stack pieces

nearly-headless — product + manager

Central UI for sessions, providers, projects, and tasks. The manager agent runs here: watches worker progress, maintains .hyperspace/*.html, surfaces pending work, sends your steering input back to the right provider session.

Borrow t3code's session model; skip its chat UI thesis.

agent-comms — optional nervous system

When the manager, provider host, and artifact generator are separate processes, agent-comms gives them a shared event log and command queue. nearly-headless publishes session/run events; the manager subscribes and updates artifacts.

Not required if everything collapses into one nearly-headless server — but helps gemma-gem and future harnesses participate without tight coupling.

gemma-gem — local artifact generator candidate

On-device Chrome extension. Could run the lightweight "read events → update HTML" loop without spending Codex tokens. Inference and DOM tools stay in the extension; nearly-headless remains the canonical session manager.

Provider adapters — Codex, Claude, Cursor

Start with native CLI protocols (codex app-server, etc.) like t3code. Workers stream through nearly-headless; manager interprets — workers never touch artifact HTML.

Artifact update policy

  • Update on milestones — turn complete, checkpoint, blocked, needs input, session status change
  • One dashboard per project — not one HTML file per commit
  • Incremental patches — manager edits sections, not full regenerations
  • User interactions persist — comments and form state saved in artifact HTML, routed back as structured prompts
